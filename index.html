For fun: ideas for Fredrin

Proof, not passing tests

Tests are increasingly written by the same AI that wrote the code, so a green check proves less than it used to. Video or screenshots of the change actually working are worth more.

  • Fredrin already runs its own VM. Make proof the opinionated default: every PR spins up its own instance of the app there.
  • Each PR keeps scripts that bring the app up, seed data for the test, and a plain description of what to check.
  • An AI drives the change like a user would and records it. The video goes on the PR as the evidence.

Bugs that validate themselves

Connect Fredrin to Linear or whatever ticket system a team already uses.

  • When a bug comes in, an AI reproduces it, captures the console errors, and suggests where in the code the fix probably lives.
  • Confirmed bugs can kick off a fix PR automatically. It starts to feel like a factory.

Promote features, not environments

The usual flow merges a feature branch into an intermediate environment, then promotes the whole environment. Someone else's broken code can keep yours from reaching prod.

  • Instead, environment + feature branch makes a new ephemeral branch. Fredrin runs the tests on it and records the specific change as proof.
  • Going from the intermediate environment to prod, it does the same thing again before merging.
  • Features get promoted on their own, without the whole environment branch having to be good. Essential for hotfixes, and just nicer every day. Almost a superset of git.
  • I built this at a previous company, where we called it Lorax, and it went well.

Run it like a kitchen

Coding with agents is more like being a head chef. A kitchen has stations, and Fredrin should surface each one: feature writers, PR reviewers, issue validators and so on.
